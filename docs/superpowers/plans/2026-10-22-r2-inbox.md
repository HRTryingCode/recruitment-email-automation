# R2 Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One keyboard-first Inbox page (rail · list · reply pane) on top of the U0 inbox API, replacing the Drafts tab and the Dashboard "Quick triage".

**Architecture:** A new `InboxPage` owns URL state (`view`, `mailbox`, `item`), polls `GET /api/inbox` every 15 s and renders `InboxRail`, `InboxList` and `ReplyPane`. All mutations (send/undo/dismiss/snooze/batch) go through one `useInboxActions` hook that handles 423 locks, optimistic removal and auto-advance. Pure logic (labels, snooze presets, evidence highlight, diff, send line) lives in `lib/inbox.ts` and is unit-tested; components are tested with RTL + msw against the real `lib/api.ts`.

**Tech Stack:** React 18, react-router 6, TanStack Query 5, shadcn (radix-luma, taupe) on Tailwind 3, sonner, Vitest + RTL + msw 2, Playwright for screenshots.

**Spec:** the R2 brief (Andriy, 2026-10-22) — reproduced in the PR body; U0 API: PR #82 / `frontend/src/lib/api.ts` "U0 inbox" section.

## Global Constraints

- Only `@/components/ui/*` primitives; no raw `<button>/<input>/<textarea>/<kbd>/<label>`, no palette/legacy colour classes, no `rounded-*`/`shadow-*`/`z-*`, no arbitrary values, no inline `style` (docs/DESIGN-SYSTEM.md §5). R2 files go strict in `hotspots.test.ts`.
- Full taupe: semantic colours only — green `success` = Interested, amber `warning` = Unsure, red `destructive` = Not interested. Add `--success`, `--warning` (+ `-foreground`) to `index.css` light/dark + `tailwind.config.ts` (R1 owns them long-term; same names).
- Label chip text is exactly `Interested` / `Unsure` / `Not interested`; never a percentage.
- Send = `POST /drafts/:id/send {undoSeconds: 10}`; toast `Sending to <name> · Undo` with a 10 s countdown. No Approve anywhere.
- Dismiss reasons (exact labels → API): Wrong label → `wrong_label`, Spam → `spam`, Already handled → `already_handled`, Not needed → `not_needed`, Other → `other`.
- Snooze presets: Later today (+3 h, capped at 23:59 ET), Tomorrow 9am ET, Next week (next Monday 9am ET), Custom date (date input → 9am ET that day).
- Presence heartbeat every 15 s (`viewing`, or `editing` when the textarea is focused or dirty); `DELETE` on item change/unmount and on `pagehide` (fetch keepalive).
- 423 → blocking inline Alert "`<name>` is editing this reply" + "Send anyway" (retries with `override: true`). Never silent.
- Shortcuts: ↑/↓ prev/next, ↵ open, E edit, ⌘↵ send, ⌘Z undo, D dismiss, S snooze, Esc close/back, ⌘K palette, ? help; j/k silent aliases. Only ⌘↵ and Esc fire while typing.
- URL: `/inbox?view=…&mailbox=…&item=<draftId>`; legacy `?draftId=` maps to `item`.
- Send line: `Sending as <mailbox> · CC <first name or "no one"> · Lever: no change`.
- Quick rewrites use `POST /drafts/:id/dictate {notes}` (the U0 instruction-rewrite endpoint; marks the body as edited and keeps `aiBodyText`), after first saving unsaved edits. Plain "Regenerate" uses `regenerate {keepEdits: true}`. No backend change.
- No new Lever calls (LeverBadge + AddToLeverButton only). No migration. Never log bodies.

## Review Focus

1. Sending while the editor has unsaved text → the send must carry `bodyText` (test in Task 6).
2. Acting on the last item in a view → auto-advance falls back to the previous item, then to the empty state (Task 6).
3. 423 on dismiss/snooze, not just send → same Alert, override replays the same action (Task 6).
4. Typing "d"/"s"/"e" inside the editor or rewrite input must not dismiss/snooze (Task 4).
5. `?item=` pointing at an item not in the current view (e.g. legacy `draftId` of a snoozed draft) → pane still loads it via `GET /drafts/:id` (Task 5).
